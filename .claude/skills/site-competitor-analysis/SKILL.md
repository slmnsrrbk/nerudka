# Анализ конкурентов, ЦА и структура сайта

Скилл описывает полный цикл: от снимков чужих сайтов до утверждённой структуры главной и внутренних страниц.
Результат каждого этапа живёт в трёх местах сразу:

1. **JSON** — единственный источник данных (`competitors/analysis.json`, `competitors/audience.json`).
2. **Markdown** — читаемый отчёт, собирается из JSON скриптом (`competitors/ANALYSIS.md`, `competitors/AUDIENCE.md`).
3. **Figma** — те же данные таблицами и схемами на странице «Аналитика», для клиента и дизайнера.

Руками в MD и Figma цифры не правят: меняют JSON, пересобирают MD и перестраивают таблицу в Figma.

## Правила, которые не нарушаем

- **Только проверяемые факты.** У каждой цифры, цитаты и формулировки есть источник со ссылкой: сайт конкурента, снимок, статья, отзыв. Формулировки конкурентов приводим как на их сайтах, в кавычках.
- **Ничего не выдумываем.** Ни интервью, ни людей, ни цитат, ни цифр клиента. Чего нет — пишем `[заглушка]`. Сегменты называем гипотезой, пока их не подтвердили данные клиента (CRM, заявки).
- **Источник недоступен из рабочей среды** (сайт закрыт сетевой политикой, факт взят из поисковой выдачи) — ставим звёздочку: `S12*`. Перед показом клиенту такие ссылки открывают и перепроверяют.
- **Дата снятия** указываем в каждом отчёте: сайты меняются.
- Сайт не открылся (блокировка хостинга, ошибка) — так и пишем в строке таблицы, сайт из выборки не убираем.
- Отчёт пишем простым языком для клиента: без жаргона, короткие предложения, вывод — первым.

Дальше — как делать каждый этап.

### 1. Выборка конкурентов

- Берём сайты из выдачи Яндекса и Google по главным запросам ниши в регионе клиента, плюс сайты, которые назвал клиент (включая его собственные).
- 12–20 сайтов достаточно. Каждому даём номер и slug: `01-gmr-beton`. Номер потом используем везде: в таблицах, матрице, скриншотах.
- Отдельно помечаем «свои» сайты клиента: с ними делаем сверку в обоснованиях вариантов.

### 2. Снимки (`scripts/shoot-competitors.mjs`)

- Playwright, Chromium, `locale: ru-RU`, обычный десктопный user-agent.
- Три снимка на сайт: первый экран 1440×900, вся страница 1440, мобильная версия 390×844 (`isMobile: true`).
- Перед полным снимком прокручиваем страницу до конца с паузами: иначе ленивые блоки не загрузятся.
- **Сеть.** Если из контейнера чужие домены закрыты (прокси отвечает 403), скрипт запускаем на раннере GitHub Actions вручную (workflow `competitor-shots.yml`, параметр `script`). Результат коммитится в репозиторий. Обходить сетевую политику контейнера нельзя.

### 3. Автоматический аудит главной (`scripts/competitor-audit.mjs`)

Скрипт открывает главную (3 попытки, пауза 9 с, прокрутка) и выгружает в `competitors/audit/<slug>.json`:

| Поле | Как извлекаем |
|---|---|
| `title`, `description`, `height` | `document.title`, meta description, `scrollHeight` (длина страницы в px — важный показатель «простыни») |
| `header`, `nav` | текст шапки, пункты верхнего меню |
| `firstScreen` | видимый текст до 900 px без шапки |
| `sections[]` | секции по заголовкам `h1/h2` (если их меньше 5 — ещё `h3`): заголовок, уровень, верх, высота, текст до 1500 символов; в каждой — число форм, полей, картинок, таблиц, подписи кнопок, iframe |
| `forms[]` | поля (placeholder или name) и текст кнопки |
| `fixed` | закреплённые элементы: плавающие кнопки, плашки |
| `prices`, `discounts`, `facts` | регулярки по тексту: цены «от … ₽», упоминания скидок, факты (миксеры, ИНН, ГОСТ, лаборатория, 24/7, «с 20xx») |
| `features` | Telegram / WhatsApp / MAX / VK по ссылкам, телефоны, корзина, квиз, калькулятор, видео, чат-виджеты (Jivo, Битрикс24, Envybox, Marquiz…), CMS по признакам в HTML, виджет отзывов |

Плюс снимки всей страницы кусками по 8000 px в половинном масштабе (`-p1.jpg`, `-p2.jpg`…): их удобно класть в Figma и читать глазами.

Автоматике не верим вслепую: каждую строку проверяем по снимкам на этапе 4.

### 4. Ручной разбор каждого сайта

Для каждого сайта заполняем карточку в `analysis.json → sites[]`:

```json
{
  "id": "01", "name": "GMR Group", "url": "https://gmr-beton.ru/",
  "cms": "WordPress", "height": 19016, "family": "A",
  "hero": "Оффер и цена первого экрана словами сайта",
  "leads": "Формы и лид-магниты", "trust": "Доказательства доверия", "contacts": "Каналы связи",
  "structure": ["Шапка: …", "Первый экран: …", "…блоки сверху вниз…", "Подвал: …"],
  "good": ["что хорошо для продаж"], "bad": ["слабые места"], "take": ["что можно взять"]
}
```

- **Структура** — все блоки главной по порядку, одной строкой каждый: что в блоке и как он продаёт. SEO-тексты помечаем `(SEO)`.
- **Хорошо / слабо / взять** — по 2–5 пунктов, конкретно: «Квиз ведёт начальник производства с фото», а не «хороший квиз».

### 5. Сводная таблица

Строка — сайт, колонки: **Сайт** (номер, название, домен, CMS, длина страницы, семейство) · **Первый экран** · **Формы и лид-магниты** · **Доверие** · **Контакты**.
Второй таблицей: **Сайт** · **Что хорошо для продаж** · **Слабые места** · **Что можно взять**.

### 6. Матрица блоков

- Строки — типы блоков (в примере 35): форма в первом экране, цена «от» в первом экране, квиз, калькулятор, прайс на главной, корзина, «нашли дешевле», завод против перекупщика, лаборатория, видео завода, автопарк, доставка по зонам, карта заводов, отзывы, объекты, сертификаты, договор скачать, юрлицам, FAQ, SEO-текст посреди страницы, финальная форма и т. д.
- Колонки — сайты по номерам, последняя — **Всего**.
- В ячейке `●`, если блок есть на главной.
- По колонке «Всего» делим блоки:
  - **база рынка** — есть у большинства (примерно от половины выборки), должно быть и у нас;
  - **редкие сильные ходы** — у 1–3 сайтов: кандидаты в идеи;
  - **частые ошибки** — например, SEO-текст посреди продающих блоков.

### 7. Семейства шаблонов

Ищем сайты с одинаковым контентом, вёрсткой или CMS-шаблоном (сеть одного владельца, одна студия). Помечаем буквой (A, B, C…) в таблицах. Вывод для клиента: от каких шаблонов уходить, чтобы не выглядеть «как все».

### 8. Выводы

Три подраздела:

1. **База рынка** — с числом «у 11 из 13».
2. **Идеи, которые можно взять** — таблица `№ · Идея · Источник` (И1…Иn), источник — номер и название сайта.
3. **Чего избегать** — с примерами сайтов.

Сверху отчёта — «Коротко»: 4–6 главных выводов списком.

### 9. ЦА: источники и сегменты

- **Источники** нумеруем `S01…Sn`: FAQ на главных конкурентов (это вопросы, которые заводы сами вынесли на сайт: сигнал косвенный, но повторяющийся), отзывы (Отзовик, Яндекс Карты), статьи о выборе поставщика и типичных обманах, обзоры рынка. У каждого — название и URL.
- **Сегменты** `С1…С5` — гипотеза с основанием (какой источник делит клиентов так же). Для каждого: кто это, задача, что говорят и спрашивают (только из источников), источники.
- Доли сегментов берём только из данных клиента. Пока их нет — пишем `[заглушка]`.

### 10. Вопросы клиента Q01–Q20

- Формулируем голосом клиента: «Сколько будет стоить с доставкой ко мне?», «Вы сам завод или перекупщик?».
- Каждый вопрос: сегменты, к которым он относится, и источники, где он встречается.
- 20 вопросов — рабочий размер: покрывает все сегменты и помещается в одну таблицу.
- Приложить **гайд для настоящих интервью**: по 5–7 человек на сегмент, 20–30 минут, 6–8 открытых вопросов о последнем заказе. Кого звать: недавние клиенты из CRM и те, кто оставил заявку, но не купил. Ответы потом раскладываем по Q01–Q20.

### 11. Варианты структуры главной П1–П6

- 4–6 концепций с разной главной идеей: «проверяемый завод», «конфигуратор цены», «люди и объекты», «диспетчерская», «каталог по задачам», «для застройщиков».
- Каждый вариант — серый прототип 1440 px в Figma, блоки сверху вниз.
- Для каждого блока — **обоснование**:
  - **Зачем** — какую задачу клиента решает;
  - **Откуда взято** — сайт-конкурент, источник или наша идея;
  - **Отвечает на** — номера вопросов Q.
- Отдельная карточка «Сверка с вашими сайтами»: структура текущих сайтов клиента и что у нас вместо.

### 12. Покрытие вопросов

- Таблица `вопрос × вариант`: ответ есть прямо в блоке или нет.
- Итог по варианту — «16 из 20». Итог по сегменту — «8/9».
- Выписываем вопросы, на которые не отвечает ни один вариант, и расхождения в данных (пример: калькулятор считает запас 3 %, а статья — 5 %).

### 13. Варианты v2 и итоговый вариант

- **v2.** Пробелы каждого варианта закрываем блоками из других вариантов или фактами из данных сайта, пока он не ответит на 20 из 20. В ключах блоков указываем происхождение: `o:NN` — свой блок, `c:П5v2:04` — блок, перенесённый из другого варианта. Варианты v1 не трогаем: v2 кладём рядом.
- **Итоговый вариант.** Таблица `# · Блок · Отвечает на · Зачем / SEO`, плюс обоснование по официальным рекомендациям поисковиков со ссылками:
  - [Яндекс Вебмастер: представление информации](https://yandex.ru/support/webmaster/ru/recommendations/presentation.html) — один H1 с основным запросом и логичные подзаголовки;
  - [Яндекс Вебмастер: структура сайта](https://yandex.ru/support/webmaster/ru/recommendations/site-structure.html) и [ссылки](https://yandex.ru/support/webmaster/ru/recommendations/links.html) — внутренние ссылки;
  - [Google SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) — разделы с заголовками;
  - [Google: LocalBusiness](https://developers.google.com/search/docs/appearance/structured-data/local-business) — разметка адресов.
- После правок клиента фиксируем, что убрали и что добавили, со ссылкой на сайт-образец.

### 14. Структура всего сайта

- **Дерево каталога** строим по семантике клиента (у нас — XMind заказчика, перенесён в `src/lib/menu.ts`): разделы, категории, подкатегории, страницы марок и назначений.
- Таблица страниц: `Страница · Адрес · Шаблон · Макет в Figma`. На сайте только страницы, у которых есть макет.
- Внутренние ссылки: каждая страница каталога достижима обычной ссылкой (меню, хлебные крошки, подвал, ссылки из блоков).

### 15. Сверка макета с сайтом

- На сайте замеряем высоту каждой секции на 1440, 768 и 320 (Playwright, `getBoundingClientRect`), в Figma — высоты фреймов секций. Сравниваем по номерам секций.
- Порог расхождения — 3 px. Всё, что больше, разбираем: обычно это перенос текста или неверный HUG / FILL в автолейауте.
- Проверяем горизонтальную прокрутку на ширинах 320–2560 (`npm run check:home`, `check:mobile`).

## Как оформить в Figma

Всё кладём на одну страницу **«Аналитика»**. Каждый этап — отдельная **Section** с номером и названием, по вертикали сверху вниз, с отступом 400–600 px между секциями:

| Section | Что внутри |
|---|---|
| `1 · Конкуренты — скриншоты` | колонки по сайтам: номер и название, первый экран, вся страница, мобильная версия |
| `2 · Анализ конкурентов` | фреймы `1 · Сводная таблица`, `2 · Матрица блоков`, `3 · Общий вывод`, `4 · Структура каждого сайта` |
| `3 · ЦА: вопросы клиентов и блок-схемы` | `0 · Как читать`, `1 · Сегменты`, `2 · 20 вопросов × сегменты × варианты`, `3 · Блок-схемы П1–П6` |
| `4 · Прототипы главной v1 (П1–П6)` | прототипы 1440 px, справа от каждого — колонка «Обоснование · Пn» шириной 580 |
| `5 · Прототипы v2 и итоговый — 20/20 вопросов` | прототипы v2, метка над каждым, справа — «Блок-схема · Пn v2» |

В каждой секции первым идёт фрейм **«0 · Как читать»**: 3–6 строк, что здесь, как читать цвета и значки, где исходные данные.

### Общие правила вёрстки

- **Только автолейаут.** Таблица — вертикальный автолейаут из строк. Строка — горизонтальный автолейаут из ячеек. Ячейка — вертикальный автолейаут с текстом. Никаких абсолютных координат внутри таблиц.
- **Размеры.** Ячейки — `FIXED` по ширине (ширина колонки) и `FILL` по высоте, чтобы строка росла по самой высокой ячейке. Строки и таблица — `HUG`. Тексты в ячейках — `FILL` по ширине, авто-высота.
- В `HUG`-контейнере не ставим `SPACE_BETWEEN` (зазор игнорируется) и не кладём `FILL`-детей (схлопываются).
- **Имена слоёв** осмысленные: строка называется как сайт или вопрос («01 · GMR Group», «Q07»), фреймы — по содержанию. Не оставляем «Frame 123».
- **Шрифт** — Inter (или шрифт проекта). Заголовок фрейма — Bold 32, подзаголовок — Regular 14–16 серым, текст ячеек — Regular 13, шапка таблицы — Semi Bold 13 белым.
- Ссылки на сайты — синим (`#2b59c3`), служебное (CMS, длина страницы) — серым (`#8a8f99`).

### Карточка-обёртка таблицы

```
FRAME «1 · Сводная таблица»     VERTICAL, gap 24, padding 48, fill #ffffff, radius 16, HUG
├─ TEXT «1 · Сводная таблица: N конкурентов»   Inter Bold 32
├─ TEXT пояснение (как читать)                  Inter Regular 14, #5e6470
└─ FRAME «Таблица»              VERTICAL, gap 0, radius 10, stroke 1 px, clip
   ├─ FRAME «Заголовок»         HORIZONTAL, fill #16181d
   │  └─ ячейки: VERTICAL, padding 14/16, FIXED × FILL, текст Semi Bold 13 #ffffff
   ├─ FRAME «01 · GMR Group»    HORIZONTAL, fill #ffffff
   ├─ FRAME «02 · МосАвтоБетон» HORIZONTAL, fill #f7f6f2   ← зебра через строку
   └─ …
```

Между ячейками — тонкая обводка 1 px (правая и нижняя).

### Структура каждого сайта

Горизонтальный ряд колонок шириной 420, зазор 24. В колонке сверху вниз:

1. Тёмная плашка (`#16181d`, radius 10): номер, название, домен, CMS и длина.
2. Светлая карточка (`#f7f6f2`, radius 10): блоки главной списком по порядку, ниже «Хорошо», «Слабо», «Взять».
3. Фрейм «Скриншот главной» (stroke 1, radius 8): куски снимка `-p1…-p3` один под другим.

### Сегменты

Ряд карточек шириной ~517 (белые, radius 12, stroke 1, padding 24): чип сегмента и название, кто это, «Основание: S02», «Что говорят и спрашивают» — пункты со ссылками на источники.

### Прототипы и обоснования

- Прототип варианта — фрейм 1440 серым (без финального дизайна), имя «П1 · Проверяемый завод — цена до звонка и доказательства».
- Над прототипом — **метка**: «П1 v2 · Проверяемый завод · 20/20». Итоговый вариант выделяем зелёной меткой.
- Справа — колонка **«Обоснование · П1»** шириной 580 из карточек по блокам, напротив своего блока:
  - карточка блока: жёлтая (`#fffbea`, stroke, radius 10, padding 16/20), заголовок «01 · Первый экран» Bold 15, подписи «Зачем» и «Откуда взято» Semi Bold 12 (`#8a6d00`), текст Regular 13.5;
  - карточка «Сверка с вашими сайтами» — зелёная (`#eef6ef`): «Их структура» и «Что у нас вместо».
- В v2 внутри каждого блока прототипа — жёлтая аннотация «зачем блок» и синяя строка «Отвечает на вопросы: Q01, Q05…».

### Блок-схема варианта

Фрейм «Блок-схема · П1 v2» шириной 580 (белый, radius 12, stroke 1, padding 24):

- заголовок Bold 24 и строка «Отвечает на 20 из 20 вопросов клиента»;
- ряд чипов сегментов с покрытием;
- карточки блоков сверху вниз (radius 8, stroke 1, padding 12), между ними стрелка-вектор. В карточке:
  - «00 · Шапка — одна строка, без мега-меню» Semi Bold 14;
  - под заголовком плашки вопросов (`#eef0f4`, radius 6): номер Semi Bold 12 (`#44506a`) и текст вопроса.

В Markdown та же схема — блоком `mermaid` (`flowchart TD`).

### Скриншоты в Figma

Снимки загружаем как изображения в фреймы колонок (в Figma-MCP — `upload_assets`). Если Figma недоступна из контейнера, загрузку делает раннер GitHub по одноразовым ссылкам (workflow `figma-upload.yml`). Ссылки живут 10 минут и срабатывают один раз, поэтому workflow запускаем сразу после выдачи ссылок.

## Markdown-отчёты

- `ANALYSIS.md`:
  - ссылка на Figma и содержание с якорями;
  - «Коротко»;
  - сводная таблица и «Что хорошо и что взять»;
  - структура каждого сайта: блоки, плюсы, минусы, что взять, ссылки на скриншоты;
  - матрица блоков;
  - общий вывод;
  - «Как собраны данные» с датой.
- `AUDIENCE.md`:
  - «Как собрано» (честно: интервью нет, сегменты — гипотеза);
  - сегменты, 20 вопросов, покрытие, блок-схемы (`mermaid`);
  - v2 и итоговый вариант с SEO-обоснованием;
  - гайд для интервью;
  - нумерованный список источников.
- Оба файла собираются скриптами (`scripts/analysis-md.py`, `scripts/audience-md.py`) из JSON. Перед коммитом пересобираем и смотрим diff.
